# VeriPacket — Claude Code Project Instructions

## Mission

VeriPacket is an educational, security-focused binary packet parsing library written in **safe Rust**, with formally verified functional properties using **Charon → Aeneas → Lean 4**. Keep the initial implementation deliberately small and verifiable. Correctness, clear specifications, and reproducible tooling matter more than features or performance.

This repository uses **Nix Flakes** to manage the development environment declaratively. Do not tell contributors to install a global Rust, Charon, Aeneas, or Lean version to work around a mismatch.

## Technology stack

| Technology | Responsibility |
| --- | --- |
| Rust | Source of truth for production parser implementation |
| Cargo | Rust builds and unit tests |
| rustfmt / Clippy | Rust formatting and static checks |
| Charon | Extract Rust crate into LLBC (`.llbc`) |
| Aeneas | Translate LLBC into Lean 4 definitions |
| Lean 4 | Express specifications and check proofs |
| Lake | Build Lean modules and manage Lean dependencies |
| Nix Flakes (`flake.nix`, `flake.lock`) | Pin and provide compatible development tools |
| direnv + nix-direnv (optional) | Activate the development shell automatically |

### Verification trust model

- Rust code is compiled and tested normally; Lean does **not** execute production Rust.
- Charon extracts the Rust program, and Aeneas translates the result into a functional model in Lean.
- Lean's kernel checks theorems about the generated model. Verification is conditional on the accuracy and assumptions of the extraction/translation pipeline and any external models.
- `lake build` succeeding is **not** equivalent to every program property being proved. Track theorems and assumptions explicitly.
- Aeneas primarily supports a subset of safe, sequential Rust. Avoid `unsafe`, async, concurrency, function pointers, unsupported library abstractions, and unnecessarily complicated borrowing in the verified core. Validate actual support before adopting new language features.

## Initial project scope

Use this conceptual packet format, subject to explicitly documented decisions:

```text
+----------------+-------------+--------------------+
| length (u16 BE)| kind (u8)   | payload (0..N bytes) |
+----------------+-------------+--------------------+
```

- `length` is the number of bytes **after** the 2-byte length header, including the 1-byte `kind` field.
- Minimum valid packet length is 3 bytes.
- Only accept a packet when the actual number of bytes after the header equals the declared length.
- Reject invalid input cleanly; never panic on malformed data.
- Keep a low-level `validate_header` / `valid_packet` function separate from higher-level parsing and I/O.
- Do not add a network server, sockets, `tokio`, cryptography, or protocol extensions until the initial correctness properties are proved.

### Verification milestones

1. **M0: Foundation** — Nix shell, Cargo project, Lean project, compatible pinned tools, and instructions. Commit `flake.lock` and `Cargo.lock` (if present).
2. **M1: Minimal validator** — Safe Rust function validating three-byte minimum and declared length; boundary-focused unit tests.
3. **M2: Translation** — Charon produces `.llbc`; Aeneas generates Lean; generated files compile with Lake. Record any external model obligations.
4. **M3: First proofs** — Prove that every accepted packet has a minimum valid length and consistent declared length; prove malformed short packets are rejected and the function returns normally for modeled inputs.
5. **M4: Parsed structure** — Return a typed packet; prove the validated metadata agrees with source bytes and payload boundaries.
6. **M5: Automation** — Add a script and CI checks to regenerate extraction, build all proofs, and detect stale generated code.

## Reproducible environment rules

- Enter the environment with `nix develop`. Optional automatic activation: `direnv allow` after installing/configuring direnv and nix-direnv.
- Use Nix's `flake.lock` as the pinned source for Aeneas, Charon, nixpkgs, and their matching Rust compiler. Do not use `nix run github:...` without a pinned reference in repeatable builds.
- The flake provides `aeneas`, `charon`, the Charon-compatible Rust toolchain, `elan` (Lean toolchain manager), `git`, and other local utilities.
- Lean itself is selected by `proofs/lean-toolchain`, copied from the exact Aeneas source revision. `elan` may fetch that toolchain on first use; see the reproducibility caveat below.
- The Lean `aeneas` Lake dependency must point to the **same Git revision** as the locked Nix Aeneas input, ideally with a matching `rev` in `proofs/lakefile.toml`. Don't silently use separate moving `main` branches.
- To inspect the pinned Aeneas source path in the shell, use `$AENEAS_SOURCE` (provided by `flake.nix`). This is a Nix store source path, not necessarily a writable checkout.
- Copy the backend's toolchain file with: `mkdir -p proofs && cp "$AENEAS_SOURCE/backends/lean/lean-toolchain" proofs/lean-toolchain`.
- Initial setup: `nix flake lock`, then `nix develop`. Commit the resulting `flake.lock` to Git.
- For stricter fully offline reproducibility, packaging Lean as a Nix derivation or using a Nix-managed Lean toolchain is a **future task**. Pinning `lean-toolchain` fixes the version but `elan` can still download artifacts; don't describe that as a fully Nix-built Lean compiler.
- Changing Aeneas or the Charon/Rust toolchain is a deliberate upgrade requiring regeneration and replay of all proofs.

## Day-to-day workflow

Run these from the project root **inside `nix develop`**:

```sh
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-features
```

Translation after setting up Cargo, Lean package files, and necessary external models:

```sh
charon cargo --preset=aeneas --dest-file=veripacket.llbc
aeneas -backend lean veripacket.llbc \
  -dest proofs -subdir /VeriPacket/Code \
  -split-files -namespace VeriPacket
(cd proofs && lake build)
```

Note: Aeneas may generate `*_Template.lean` files for unavailable external models. Copy these to the corresponding actual `.lean` filenames **only when needed**, implement and audit their semantics, and keep them separately from generated output. The first proof must be based on the **real generated function names/signatures**, not guessed Lean definitions.

After an edit to Rust affecting verified behavior: regenerate LLBC, regenerate Lean, review changes, and rerun all proofs. Simply running `lake build` on old generated files does not verify the updated Rust source.

## Formal proof policy

For every verification claim:

1. State the *preconditions*, *postconditions*, and what happens on invalid input.
2. Write the specification in `proofs/VeriPacket/Spec/` and the proof in `proofs/VeriPacket/Properties/`.
3. Keep human-authored proofs outside generated `Code/` files.
4. Use the Aeneas-generated definitions and primitives; inspect `Funs.lean` and `Types.lean` instead of inventing type signatures.
5. Prefer small theorems about narrow helper functions; use helper lemmas for arithmetic and length reasoning.
6. No `sorry`, `admit`, `native_decide` used as a shortcut to avoid proof obligations, or unreviewed `axiom` declarations in accepted proofs. Audit `#print axioms` for important final theorems.
7. Report a theorem as **verified** only after the Lean checker accepts its complete proof, no placeholders remain, and its dependencies/assumptions have been reviewed.
8. If a proof does not compile, provide the exact diagnostic and fix the proof, specification, or model. Never weaken a security property just to make a build pass.
9. Distinguish memory safety supplied by Rust from the semantic correctness guarantees established by the Lean theorem.

## Coding conventions

### Rust

- Prefer stable, idiomatic, straightforward **safe** Rust supported by Aeneas.
- Separate pure packet validation and parsing from I/O and application orchestration.
- Use explicit checked arithmetic for computations that can overflow; document packet length units.
- Never use unchecked indexing unless the preceding validation makes it demonstrably safe; prefer checked access or explicit guards.
- Write tests for empty, truncated, exactly minimal, valid longer, inconsistent lengths, and maximum representable lengths.
- Avoid dependencies for trivial functionality. Add dependencies only with a clear reason and compatibility review.
- Public APIs and data formats require concise Rustdoc.

### Lean

- Maintain parity between Rust function behavior and the generated Lean model.
- Isolate mathematical statements from tactic-heavy implementation details.
- Keep proof names descriptive (`accepted_implies_min_length`, `accepted_length_matches_header`).
- Rely on kernel checking rather than claims that a solver or LLM has "verified" something.

### Nix

- Keep `flake.nix` declarative and `flake.lock` tracked.
- Never let Claude run `nix flake update` as a casual setup or cleanup step: it changes the toolchain.
- Avoid global package installations (`cargo install`, `rustup`, `pip install`) as prerequisites. Introduce pinned Nix packages or project-local configuration where practical.
- Do not assume network access; report when Nix or elan needs to fetch pinned dependencies.

## Agent workflow and definition of done

Before changing code: identify which milestone applies, whether the change affects an existing specification, and whether the Rust fragment is supported by Aeneas. Implement the smallest change that satisfies the requested goal.

After changes, run (when available):

1. `cargo fmt --all -- --check`
2. `cargo clippy --all-targets --all-features -- -D warnings`
3. `cargo test --all-features`
4. Charon extraction and Aeneas translation for changed Rust
5. `(cd proofs && lake build)` for checked Lean proofs
6. Review newly generated external-model obligations and verify proof source is not stale

If any command cannot be run, say so precisely. Never say code or proofs were checked unless the commands actually ran. Keep the verification status explicit: **not yet modeled**, **model generated**, **proof pending**, or **proof checked**.
